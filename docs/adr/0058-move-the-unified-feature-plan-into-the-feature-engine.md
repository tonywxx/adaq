# Move the unified Feature Plan into the Feature Engine

ADAQ M10 replaces the pre-v1 consumer-only `FrozenFeaturePlan@1.0.0` with one `Feature Plan@2.0.0` owned by the new Tauri-independent `adaq-feature-engine`. The Plan represents reusable Definition DAGs, Feature Scopes, availability, missingness, Warmup, Fitted Transformation Artifacts, exact engine identities, and ordered Component bindings, while each Feature Materialization Request separately binds the exact Snapshot, Point-in-Time Instrument Universe, observation range, and Seed. The same Plan semantics serve historical materialization, Factor research, Model training and inference, Backtest, and Paper Trading; `adaq-component-tooling` becomes a Manifest-to-Plan adapter, `adaq-indicator-engine` remains a specialized subengine, and application commands only create/query Attempts while cancellable blocking workers execute them. This supersedes ADR 0012's Plan 1.0 schema and ADR 0020's Plan ownership, while retaining canonical JCS hashing, authoritative Slot order, finite dense Component inputs, and the existing Indicator Engine boundary. Because ADAQ remains pre-v1, incompatible stored Plan evidence is rejected with an explicit device-level Reset requirement rather than migrated, dual-read, or automatically deleted.

Plan and Definition documents remain bounded to 1 MiB of canonical JSON, 256 DAG nodes, 64 ordered outputs, 64 dependency depth, and 100,000 effective Warmup Bars. Exact Dataset row, memory, and concurrency ceilings must come from M10 benchmarks rather than speculative constants.

The core exposes batch materialization and stateful observation evaluation through the same Plan and operator state machine, with equivalence tests across chunking, gaps, and restarts; M10 adds no Paper Provider or Bot integration. New M10 Feature Definitions cannot consume Factor outputs, so the research dependency remains Feature Dataset to Factor research, while the Component adapter preserves existing Strategy and Model Feature Slot bindings to external Factors without allowing a Definition cycle. Validation and execution failures retain typed codes, stages, node identities, Instrument and Observation Time context, and safe diagnostics rather than collapsing into Feature Unavailable or localized strings.
